## Evidence vocabulary

- **M** model/storage/helper assertion, no GUI input. **I** input-driven egui event test, possibly synthetic drag payload; not native. **N** actual native window/input in private Wayland/KWin, with screenshot/trace, isolated XDG. **P** physical KDE user-operated report, separately corroborated by process, clipboard, database/file evidence where available. **AT** observed accessibility tree and assistive technology operation, with roles/names/activation. Paint bounds/screenshots are distinct from model state. Historical P is not a fresh run or automatic native input. Every scenario below is **open for this gauntlet** until exercised on the integrated artifact; 'existing' means historical coverage or code-test presence, not a new pass.

## Reference bar: precise observations, not imported design

KDE HIG is primary; retrieved 2026-11-15. [HIG overview](https://develop.kde.org/hig/), [simple by default](https://develop.kde.org/hig/simple_by_default/), [powerful when needed](https://develop.kde.org/hig/powerful_when_needed/), [layout and navigation](https://develop.kde.org/hig/layout_and_nav/), [status changes](https://develop.kde.org/hig/status_changes/), [accessibility](https://develop.kde.org/hig/accessibility/). Layout page specifically calls for grouping related items and adapting to narrow windows; use its principles, not literal Kirigami APIs in an egui app. Evaluate simple common operations and progressive disclosure, visible status and accessible operation against the other HIG sections. HIG is higher authority than the older examples below.

- [KColorChooser](https://apps.kde.org/kcolorchooser/) describes mixing, palettes and screen picking. Directly inspected [official screenshot](https://cdn.kde.org/screenshots/kcolorchooser/kcolorchooser.png): visible swatches, spectrum, channel fields, hexadecimal field, and clear confirmation/cancellation. It supports comparing information grouping and explicit formats, not copying its older appearance or assuming its interactions.
- [Plasma Color Picker](https://userbase.kde.org/Plasma/ColorPicker) describes capture → history → format → clipboard. Its unmaintained-looking page explicitly acknowledges color-vision limitations; not a modern accessibility endorsement. It is a useful workflow comparison only.
- [Colorpicker Tray repository](https://github.com/wendellavila/colorpicker-tray) and [screenshot](https://raw.githubusercontent.com/wendellavila/colorpicker-tray/master/images/screenshots/screenshot.png) inspected: tray context plus color chooser; screenshot shows no history list. The fork is old; not a substitute for Plasma 6 HIG.
- [Coolors](https://coolors.co/) and [generator guide](https://coolors-help.zendesk.com/hc/en-us/articles/360010581980-Generate-a-palette) describe generation, locks, drag reorder and saved palettes. Directly inspected the guide's [generator image](https://res.cloudinary.com/coolors/image/upload/v1575544084/zendesk/generator_screen.png): color-dominant palette with library alongside. Guide is old and web-specific; lock-preserving regeneration is a useful comparison, whereas global Space must not override focused inputs in this app. Neither images nor code were copied.

## Candidate smallest independent slices (lead chooses after baseline)

1. **Editing feedback**: changed-value Apply/Undo/Redo, invalid correction and visible error; judge by I painted bounds + N scripts at both sizes.
2. **Swatch operations and safety**: persistent accessible lock/edit/delete and keyboard reorder, locked invariants and context-safe Space; I key/pointer regressions + N both modalities.
3. **Theme assignment truth and recovery**: explain explicit assignments/links, unresolved link recovery, preview/export reachability/overwrite; I/M link, rendering, filesystem + N.
4. **Responsive/accessibility and native integration**: size/font/scheme matrix, focus and AT inspection, only then choose implementation; no navigation redesign presumed.
5. **Integration/preservation gate**: end-to-end journey, resource/dependency, packaging/golden/cleanup. These slices may share files; lead must allocate exclusive ownership or worktrees, not parallel edit collisions. Each substantial slice gets separate builder and fresh-context critic with task scripts and artifact, not builder narrative; blind only when genuinely blinded. Stop at user stop, approved budget limit, or concrete decision boundary, never an arbitrary iteration count.

## Safety and release boundary

Private sessions and isolated data first. No human desktop input/dialog approvals, live KWin restart, host installation or settings changes, exported-theme application, publishing, push, or reference asset/code reuse without explicit authorization/license review. The lead should stop at consent boundaries, not treat private input or screenshots as physical evidence. Phase 6's unresolved third-party licensing/notices, independent reproducibility, clean-chroot, broader AT, package-identity and advertised platform gates remain open regardless of UX score. Any architectural change, automatic complete-theme generation, loss of pinned palette/collapsible history, or deviation from Rust-only/transient GUI requires explicit decision.
